# Design Decisions

## D1. Deterministic citation block instead of LLM-authored citations

Decision:

The KDS evidence block is generated by server code from retrieved chunks. The
LLM may provide only a short prefix.

Reason:

Engineering-code citations are high-risk text. The user needs to know whether
a clause came from retrieval or from model prose.

Paper value:

This is the core design contribution for hallucination control.

## D2. Provider-visible history excludes evidence quotes

Decision:

The assistant history stores prefix plus summary only. Collapsible evidence is
sent to the UI but not appended to provider-visible history.

Reason:

If a quote appears in assistant history, a later turn can paraphrase it,
misattribute it, or combine it with invented clauses.

Paper value:

This creates a testable invariant: quote bodies are absent from all provider
messages.

## D3. Prefix sanitizer as a hard backstop

Decision:

The LLM prefix is discarded if it is empty, over the length cap, or appears to
fabricate a code reference such as a KDS/AISC clause number.

Reason:

The prefix is a UX nicety, not a source of engineering authority.

Paper value:

This allows the system to keep conversational UX while bounding the LLM role.

## D4. Issue-type vocabulary follows governing limit state

Decision:

The routing vocabulary separates `shear_exceeded`, `axial_exceeded`,
`flexure_exceeded`, `strength_exceeded` for interaction, and
`drift_exceeded`.

Reason:

A single generic strength bucket loses the retrieval signal needed for
limit-state-specific KDS clauses.

Paper value:

This supports a retrieval-routing contribution, especially if the benchmark
set is expanded.

## D5. All exceeded ratios are shown, but retrieval follows the governing one

Decision:

The user-visible summary and audit log list all ratios above 1.0. Retrieval
still routes by the governing ratio.

Reason:

Users need a complete NG explanation, while the retrieval query should remain
focused on the strongest signal.

Paper value:

This is a practical design tradeoff between explainability and retrieval
precision.

## D6. Audit log is separate from chat history

Decision:

Evidence quotes are persisted in an audit store, not in provider-visible chat
history.

Reason:

The system needs reproducibility without feeding quotes back to the LLM.

Paper value:

This separates provenance from generation and can be framed as an auditability
pattern for engineering RAG systems.

## D7. Operational read policy for audit logs

Decision:

Audit reads require either an operator token or ownership by server-stamped
`record.session_id`. Quotes are redacted by default even for operators.

Reason:

The audit record contains sensitive design metadata and verbatim code text.

Paper value:

This makes the system credible for shared deployment, not just local research
debugging.
